# EVERGREEN > DOSSIER_DISCOVERY (architecture foundation, non-production)

Status: contracts and invariant tests only. No migration, reader, scheduler, route, UI, source or live behavior exists. Contract: `packages/contracts/dossier-discovery.json` (vocabulary of CLASSES) + `packages/contracts/src/dossier-discovery.ts` (pure validators). Tests: `packages/contracts/dossier-discovery.test.mjs`.

## Placement (no third path)
- Temporal architecture stays `TIME_SENSITIVE | EVERGREEN`. DOSSIER_DISCOVERY is a subsystem **under EVERGREEN**: not a temporal path, not an acquisition path, not an `evergreen_view` (`health_reference` / `research_rediscovery` stay navigation views of `source_items`), not a semantic lane.
- A candidate's temporal identity is always `EVERGREEN`. Signal freshness is separate: a fresh item may help discover a topic, and an existing TIME_SENSITIVE `source_items` row is reused as a **sensor** (no second acquisition).
- Dossier entities never live in `source_items` and never touch the closed `CHECK` lists of `0028` (`acquisition_path`, `evergreen_view`).
- Acute single event → existing TIME_SENSITIVE logic. Repeated/structural pattern or globally significant emerging issue → EVERGREEN > DOSSIER_DISCOVERY.

## Boundary chain
`SIGNAL_SOURCE_ITEM → SIGNAL_RUN → OBSERVATION → SIGNAL_AGGREGATE → CONCEPT / RELATION → CANDIDATE → CANDIDATE_SNAPSHOT → REVIEW → RESEARCH_HANDOFF`. One source item can yield many observations; non-content observations (search, burden, statistics, measured/modeled environmental data, surveillance, research activity) have no source item. Discovery ends at `RESEARCH_REQUESTED`; research is a separate future workflow.

## Open world
The contract lists classes (five domains and their concept/protocol/technology/topic classes, water facets, signal families), never concepts. Which concepts exist is runtime data. An observation that matches no known concept becomes a `PROPOSED` concept (families `NEW_HEALTH_TOPIC … NEW_RELATION`) for human review (`ACTIVE | REJECTED | PAUSED`); it is never dropped and never auto-canonical. A rejected concept matches, so it does not resurface. Names in the product brief are examples only; a test fails if any appears in the vocabulary or code.

## Rules the contract fixes
- Signal families stay separate; no opaque universal score. Missing is `UNKNOWN` (or `NOT_APPLICABLE`), never 0; measured ≠ modeled.
- Relations are discovery-only (`CO_INTEREST`, `MENTIONED_WITH`, …); `CAUSES/CURES/TREATS/IMPROVES/PREVENTS` are forbidden. A pair needs a joint signal; a triple needs a direct triple signal or a sufficiently supported pair network with independent signal support. The contract fixes only the structure (complete triangle of pairs, each with a joint signal, plus declared independent support); how much is sufficient is a future calibration policy, deliberately unset, and without a configured policy a network fails closed. Automatic depth ≤ 3.
- Quality is signal hygiene, not evidence grading; independence is counted separately (mentions, creators, platforms, independent families) with origin clusters.
- Review is human; rejection needs a reason code; review never mutates weights, source activation/cadence, registry or routing.
- Handoff after ACCEPT carries discovery facts only (no conclusion, advice, dose, verdict; persons are provenance, not subject). Nothing auto-publishes.
- No patient profiling; sources carry an access state (`APPROVED | RESTRICTED | MANUAL_ONLY | UNRESOLVED | REJECTED`).

## Deliberately not built (separate prompts)
Real sources and readers (creator platforms, search/trend data, public-health and environmental data), observation/concept/proposal/candidate/review storage (a D1 migration only when a reader needs it, additive, never widening the `0028` CHECKs), scheduler/lease/cursor reuse, signal weighting and candidate generation, Hub UI, CCOS handoff. Source activation stays lifecycle-owned and owner-approved.

## Readiness semantics (P1)
`SYSTEM_SAFETY` (live GCOS unchanged, no regression) and `DOSSIER_READINESS` (a real end-to-end dossier runtime exists) are reported separately. "Production unaffected" is never evidence that dossier is production-ready. Today: SYSTEM_SAFETY = PASS, DOSSIER_READINESS = PARTIAL (contracts only; no runtime). P1 for dossier is PASS only when its defined production gate is met.

## Durable data model: final entity map (architecture only; no SQL, no migration)
Next free migration number is `0031` (`0027` stays reserved for `localization-v2`); it is not created. Names are illustrative. Optimised for ownership, explainability, boundedness, governance and reliability, not for fewest tables. Machine-readable parts live in `dossier-discovery.json` (`identity`, `relation.member`, `alias`, `candidate.identity`, `candidate_snapshot`, `compaction`, `signal_aggregate`, `window`, `signal_run`, `lineage`, `origin_item.identity`, `review`, `storage_bounds`, `sql_design_rules`) and are enforced by `dossier-discovery.test.mjs`.

### Ownership boundary (final)
- **Acquisition sources** stay owned by the existing GCOS source lifecycle / source truth; dossier references the canonical acquisition-source id and never copies it.
- **Source actors / experts** (person, or institution where useful) are owned by **dossier discovery** in the future dossier durable store, lifecycle `PROPOSED / ACTIVE / PAUSED / REJECTED / MERGED`. One actor maps to many acquisition sources. A human ACCEPT of an actor proposal changes **only actor identity state**; source activation stays source-lifecycle owned.
- **Signal run provenance** (append-only data model) is separate from **scheduler runtime state** (lease, cursor, next_due, claim), which stays deferred (`evergreen_runtime_state` reuse = `UNDECIDED_DEFERRED`); no second scheduler.

### Identity rules
- **Relation**: explicit `RELATION_MEMBER` rows (never an opaque JSON list); member count = depth (2 = DOUBLE, 3 = TRIPLE; 4+ COMPOSITE, never automatic). Identity key = relation type + order-normalized survivor member identities; every allowed discovery semantic is symmetric, so A × B ≡ B × A; one relation per identity key; a merged member resolves to its survivor without losing relation history; a PROPOSED concept may be a member of a PROPOSED relation, and a relation with a PROPOSED member cannot be ACTIVE; membership never implies causality. No hash algorithm is chosen (`NOT_SET`).
- **Alias**: `concept_id, alias_text, normalized_alias, language, alias_type, status`; a normalized alias is **not** globally unique. Resolver: exact unambiguous match → existing concept (including REJECTED/MERGED, so a rejected or merged identity is not recreated); ambiguity (more than one distinct survivor concept, derived, not stored) → `REVIEW_REQUIRED`, never auto-merged, observation stays unresolved; no match → `PROPOSED`.
- **Candidate**: one stable candidate per target (`CONCEPT | RELATION` + id). Every evaluation appends a **snapshot**; a new candidate is never created per evaluation. Reviews are append-only events on the candidate; a REJECT persists and a later cycle does not resurface it, but snapshots (history) are still appended. Reconsideration after materially new signal, and snooze/pause resurfacing, are **not decided** (future human-governed policy); nothing is hard-coded as "never reconsider".
- **External source item**: identity key = acquisition source id + identity strategy + identity value; strategies are `SOURCE_PLUS_EXTERNAL_ITEM_ID`, `CANONICAL_URL`, `NORMALIZED_PROVIDER_KEY`, `DATASET_RELEASE_KEY`, `MANUAL_SNAPSHOT_KEY`. Only `CANONICAL_URL` needs a URL; datasets, API records and manual snapshots are valid without one. Hub-native items reuse `source_items.id`. No payload archive.

### Explainability chain and surviving compaction
`SOURCE / EXTERNAL REF → SIGNAL RUN → OBSERVATION → LIVE SIGNAL AGGREGATE → CANDIDATE EVALUATION → CANDIDATE SNAPSHOT AGGREGATE STATE → CANDIDATE SNAPSHOT`, and `RELATION → RELATION MEMBER → RELATION OBSERVATION → LIVE SIGNAL AGGREGATE → … → CANDIDATE SNAPSHOT`.
- The **live aggregate** is derived, incremental and recomputable; its membership is recoverable through its deterministic selector **only while the raw observations exist**.
- Each evaluation freezes the exact metrics it used into an immutable **aggregate state** (aggregation version, window kind and bounds, geography, family/subfamily, observation/source/actor/platform counts, commercial-context summary, measurement provenance, value + status, generated_at, an informational live-aggregate ref) plus **bounded, self-describing provenance refs** (source identity, run id, observed_at, evidence span, no raw payload). A snapshot cites aggregate states as the primary evidence and provenance refs as representative support.
- Raw compaction may touch only raw observations no snapshot requires and superseded live aggregates; it may never invalidate snapshots, aggregate states, provenance refs, snapshot signal refs or reviews. So a material snapshot stays explainable after compaction and never changes. Exact raw-membership reconstruction after compaction is **explicitly not guaranteed**. Durations, thresholds and the provenance-ref bound are `POLICY_NOT_SET`.

### Signal windows follow signal semantics
Window kinds: `FAST_7D`, `FAST_30D`, `BASELINE_90D` (fast, momentum applicable) and `SOURCE_PERIOD`, `RELEASE_PERIOD`, `STRUCTURAL_PERIOD` (no momentum). Fast families use fast kinds; burden and public-health data families are structural / release-driven (a fast kind or momentum input is invalid); environmental, research, frontier, institutional and relation signals are source-defined. WHY-NOW may combine kinds but keeps them separate; older structural data is not discarded for fast-window age.

### Review side effects
A review's effect is limited to its object type (`CONCEPT_IDENTITY_STATE_ONLY`, `ACTOR_IDENTITY_STATE_ONLY`, `RELATION_IDENTITY_STATE_ONLY`, `CANDIDATE_STATE_ONLY`). Candidate REJECT ≠ concept REJECT; relation-candidate REJECT ≠ relation identity REJECT; actor ACCEPT ≠ source activation; concept ACCEPT only via the explicit human-governed proposal lifecycle. No review autonomously mutates weights, cadence, routing, source activation or scheduler configuration.

### Provisional vs canonical identity
A newly discovered topic must be visible to humans before it is canonical. A `PROPOSED` concept, actor or relation may take part in observations, a candidate shown for review and a proposed relation, but is marked `PROPOSED` everywhere and never becomes `ACTIVE` without a human review. `MERGED` keeps history and resolves to a survivor that is neither merged nor rejected.

### Bounded storage (structural rules; durations are policy)
No full-text/transcript archive by default; reader backfill needs a configured cap; per-run fetch and item caps are required; observations are compact and deduplicated; aggregates are generated incrementally so normal candidate generation never needs a raw whole-table scan; snapshots only on evaluation or material state change; payload storage limited to provenance, a bounded evidence span and a reference; origin clusters exist only for the discovery purpose; structural data is not discarded for fast-window age; compaction never invalidates historical snapshot provenance. Raw-observation retention, compaction rules, evidence-span length and the provenance-ref bound are **unset calibration decisions** (`POLICY_NOT_SET`).

### SQL design rules for the future migration
`CHECK` only for true architectural invariants (for example, a candidate's temporal identity is `EVERGREEN`). Never encode the open-world topic universe in a `CHECK`; evolving vocabularies (window kinds, signal families, identity strategies, alias types) are validated by the contract, not by D1 `CHECK` lists that need a table rebuild to widen (the `0028` lesson). No global `UNIQUE(normalized_alias)`. `UNKNOWN` is NULL with an explicit value state, never 0. No destructive migration pattern; no `source_items` rewrite or backfill; append-only truth uses immutability triggers like `item_path_membership`.
